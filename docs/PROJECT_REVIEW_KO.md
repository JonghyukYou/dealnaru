# GameSoft 프로젝트 점검 및 4차 발표 준비

작성일: 2026-09-17

> 이 문서는 4차 발표 당시의 기록입니다. 5차 개선본의 실행법·공식 할인 수집·필터 정책·자동 갱신은 프로젝트 README를 확인하세요.

## 요약

현재 코드는 홈, 게임 검색·필터, 상세 가격 비교, 가격 이력, 규칙 기반 할인 예측, 회원가입·이메일 인증, 위시리스트, 목표가 알림, 관리자 수집, 중고마켓까지 연결되어 있습니다. 이 범위는 3차 발표에서 이미 시연했으므로, 4차 발표는 같은 화면을 반복하기보다 이후 달라진 데이터 최신성, 구매처 확장, 권한 경계, 복구 절차, 배포 설정과 Software Beta 구현을 중심으로 설명합니다.

## 관리자 계정

| 상황 | 해결 방법 |
| --- | --- |
| 초기 시드 그대로 사용 중 | 이메일 `admin@example.com`, 기존 기본 비밀번호 `admin1234`로 로그인 후 즉시 변경 |
| 관리자 이메일을 모름 | `python -m app.admin_cli list` |
| 비밀번호를 모름 | `python -m app.admin_cli reset-password --email <관리자 이메일>` |
| 관리자 행이 없음 | `python -m app.admin_cli create --email <이메일> --nickname <닉네임>` |
| 일반 회원을 관리자로 전환 | `python -m app.admin_cli promote --email <회원 이메일>` |

비밀번호 해시는 원래 비밀번호로 되돌릴 수 없습니다. DB를 초기화하거나 시드를 다시 실행할 필요 없이 해시만 안전하게 교체하는 방식이 맞습니다.

## 이번 개선본에 반영한 사항

| 구분 | 발견한 문제 | 반영 내용 |
| --- | --- | --- |
| 가격 최신성 | 5월의 종료된 80% 할인이 오늘의 특가에 남음 | 종료 시각이 있으면 실제 종료일까지 유지하고, 종료 시각이 없을 때만 7일 기준 적용 |
| 할인 종료 정보 | ITAD의 종료 정보가 DB에 저장되지 않음 | 응답의 `expiry`를 `sale_end_at`에 저장 |
| 할인 수명주기 | 새 수집에서 사라진 할인이 계속 현재가로 유지 | 응답에 없는 기존 할인을 `is_current=false`로 전환 |
| 구매처 확장 | 구매처별 수집 경로가 관리자 화면에 없음 | ITAD `shops` 필터로 GOG(35)·Fanatical(6) 선택 수집 추가 |
| 구매처 수집 실패 | 게임마다 ITAD 상세 API를 다시 호출해 프런트 15초 제한을 초과 | Deals 응답을 직접 저장해 추가 호출 제거, 수집 요청 제한을 60초로 분리 |
| 중고마켓 수명주기 | 3개월 전 수집한 매물이 계속 노출 | 서버 시작·수동 수집 시 14일 초과 행 삭제, 조회에서도 동일 기준 적용 |
| 목록 성능 | 홈·게임 목록이 모든 가격 이력을 로드 | 카드 화면은 현재 가격만 로드하고 기본 게임 목록은 DB에서 10개씩 페이지 처리 |
| 관리 화면 | 스케줄러와 개발용 버튼까지 한 화면에 혼재 | Steam·기타 구매처·중고마켓 3개 수집 행으로 통합, 수동 가격 변경·로그만 유지 |
| 안전한 데이터 정리 | 오래된 할인만 선별해 정리할 명령이 없음 | 미리보기 후 `--apply`하는 `price_cleanup_cli` 추가 |
| 데이터 안전 | 기존 `seed.py`가 실행 즉시 모든 테이블을 삭제 | `--reset`과 `RESET` 확인을 요구하도록 변경 |
| 관리자 복구 | 계정 조회·재설정 절차가 없음 | 관리자 조회, 비밀번호 재설정, 생성, 승격 CLI 추가 |
| API 보안 | 가격 시뮬레이션 API가 인증 없이 DB를 변경 | 관리자 인증 필수로 변경 |
| 알림 | `/read-all`이 숫자 ID 경로와 먼저 충돌할 수 있음 | 정적 경로를 먼저 등록하도록 순서 수정 |
| 위시리스트 | 가격 데이터가 없을 때 0원으로 목표가 도달 처리 | 실제 가격이 0보다 클 때만 도달 판정 |
| 입력 검증 | 수집 수량과 가격에 음수·과도한 값 입력 가능 | Pydantic 범위 검증 추가 |
| 이메일 인증 | 성공한 인증 토큰을 계속 보관 | 성공 후 토큰 해시와 만료 시각 제거 |
| 프런트 라우팅 | 알림·관리자 경로가 중복되고 위시리스트가 라우터 수준에서 비보호 | 중복 제거, 보호 경로 통합 |
| 신규 화면 | 소프트웨어 목록·상세 코드가 메뉴에 연결되지 않음 | 소프트웨어 Beta 메뉴와 경로 활성화 |
| 배포 설정 | API 주소가 `127.0.0.1:8000`으로 고정 | `VITE_API_BASE_URL`과 로컬 프록시 사용 |
| 운영 확인 | DB 연결 상태를 확인할 엔드포인트가 없음 | `/api/health` 추가 |
| 빌드 품질 | 초기 ESLint 결과 22개 오류, 5개 경고 | 오류·의존성 문제 정리 후 린트 통과 |
| 초기 로딩 | 모든 페이지와 차트 라이브러리를 한 번에 로드 | 페이지 단위 lazy loading으로 분할 |
| 저장소 위생 | `.env`, `venv`, 캐시가 압축 파일에 포함되고 requirements가 UTF-16 | `.gitignore`, 예시 환경파일 추가, requirements를 UTF-8로 변환 |

## 현재 미흡한 부분

| 우선순위 | 항목 | 이유와 다음 조치 |
| --- | --- | --- |
| P0 | 공유된 비밀값 교체 | 첨부 ZIP에 `.env`가 들어 있었습니다. 배포 전에 JWT·ITAD·메일 키를 모두 회전해야 합니다. |
| P0 | 실제 DB 백업과 시연 데이터 고정 | 외부 수집 결과가 발표 당일 달라질 수 있습니다. 시연 직전 DB 백업과 화면 녹화를 준비해야 합니다. |
| P1 | DB 마이그레이션 | `create_all()`은 기존 테이블 구조를 갱신하지 않습니다. Alembic을 도입해야 안전하게 배포할 수 있습니다. |
| P1 | 수집 자동화 재설계 | 발표용 관리자 화면에서는 스케줄러를 제거했습니다. 운영 자동화가 필요하면 API와 분리한 worker로 다시 도입해야 합니다. |
| P1 | 테스트 범위 확대 | 격리된 SQLite에서 핵심 테스트 13개를 통과했습니다. 다음 단계는 실제 PostgreSQL 통합 테스트와 프런트 E2E 테스트입니다. |
| P1 | 사용자 비밀번호 재설정 | 관리자 CLI는 운영자용입니다. 일반 사용자는 이메일 기반 비밀번호 재설정 화면이 필요합니다. |
| P2 | 라우터와 스키마 분리 | `main.py`가 2천 줄을 넘어 유지보수가 어렵습니다. auth, games, wishlist, notifications, admin 라우터로 나눕니다. |
| P2 | 고급 필터 성능 | 기본 게임 목록은 DB 페이지네이션으로 전환했습니다. 복합 가격·플랫폼 필터도 추후 SQL 집계로 옮깁니다. |
| P2 | 예측 검증 | 현재 예측은 할인 이벤트 평균 간격과 평균 할인율을 사용하는 규칙 기반 방식입니다. 백테스트와 오차 지표를 추가해야 합니다. |
| P2 | 소프트웨어 실데이터 | Beta 화면은 수동 데모 데이터입니다. 공식 프로모션 소스와 갱신 주기를 확정해야 합니다. |
| P2 | 구매처 직접 연동 | GOG·Fanatical 가격은 현재 ITAD를 통해 수집합니다. 향후 직접 API가 필요하면 각 서비스의 이용 조건과 인증 방식을 별도 검토해야 합니다. |
| P2 | 중고·디지털 매칭 | 상품명이 일정하지 않아 잘못 매칭될 수 있습니다. 플랫폼·에디션·패키지 상태를 포함한 정규화가 필요합니다. |

## 발표 전 권장 범위

### 반드시 할 일

1. 시연 직전 PostgreSQL을 백업하고 복구 지점 확인
2. 오래된 할인 정리 명령을 미리보기로 실행해 대상 확인
3. 정리 적용 후 홈의 오늘의 특가가 바뀌는지 확인
4. 관리자 화면의 세 줄 수집 구조와 수동 가격 변경 명칭 확인
5. GOG 또는 Fanatical 선택 수집 후 실제 구매처명이 표시되는지 확인
6. 중고마켓에 최근 14일 이내 매물만 표시되는지 확인
7. 소프트웨어 Beta의 검색·카테고리·상세 흐름 확인
8. 관리자 로그인과 `/api/health` 응답 확인, 2~3분 대체 영상 준비

### 시간이 남으면 할 일

1. 하나의 스테이징 환경에 Backend, Frontend, PostgreSQL 배포
2. 구매한 도메인의 `www`와 `api` 서브도메인 연결
3. HTTPS, CORS, 환경변수, `/api/health` 확인
4. 실제 PostgreSQL 환경에서 스모크 테스트 재실행

### 발표 이후로 미룰 일

콘솔 스토어 직접 연동, 실시간 소프트웨어 수집, 고도화된 예측 모델, 전체 라우터 분리, 사용자용 비밀번호 찾기는 짧은 일정에 비해 회귀 위험이 큽니다. 4차 발표에서는 완료한 사용자 흐름과 한계를 명확히 설명하는 편이 좋습니다.

## 배포 구조 권장안

- Frontend: 정적 호스팅 또는 CDN
- Backend: FastAPI 웹 서비스
- Database: 관리형 PostgreSQL
- Scheduler: 현재 미사용, 운영 자동화 도입 시 별도 worker
- Domain: `www.<도메인>`은 Frontend, `api.<도메인>`은 Backend

도메인을 구매한 것만으로 배포가 끝나지는 않습니다. 호스팅과 DB를 먼저 준비한 다음 DNS, HTTPS, 환경변수, CORS 순서로 연결해야 합니다.
