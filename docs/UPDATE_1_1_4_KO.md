# 1.1.4 수집 오류 진단과 관리자 로그 개선

## 달라진 내용

- ITAD 요청이 여러 스레드에서 실행되어도 최소 0.4초 간격을 공유합니다.
- HTTP 429의 Retry-After를 지킵니다. 제한 중에는 다음 게임의 이력 작업을 시작하지 않아 동일 오류 로그가 연속 생성되지 않습니다. 인증/접근 오류도 잠시 대기합니다.
- 이력 수집과 자동 갱신 결과에 실제 HTTP 상태, 시간 초과 등 오류 사유를 표시합니다. 키와 요청 URL은 진단 문구에 포함하지 않습니다.
- 완료된 수집 로그는 최근 72시간만 보관합니다. 서버 시작, 매시간, 관리자 로그 조회 시 정리합니다. 진행 중인 RUNNING 로그는 보존하며 게임, 가격 이력, 회원, 찜은 삭제하지 않습니다.
- 로그에 페이지 번호, 처음/끝, 직접 페이지 이동, 10/25/50개 표시를 추가했습니다. 보관 기간 만료로 마지막 페이지가 줄면 유효한 페이지로 이동합니다. 이전 요청이 늦게 도착해 새 페이지를 덮어쓰는 문제도 방지합니다.
- 웹의 고정 내부 IP와 자동 배정 범위를 분리해 초기 배포 때의 주소 충돌을 방지합니다.

## 오류 해석

ITAD_CONNECTION_OK는 한 건의 조회 요청이 성공했다는 뜻입니다. 전체 게임의 현재가/이력을 동시에 갱신할 때 발생한 오류까지 판정하지는 않습니다. 과거 버전은 ITAD HTTP 오류를 일반 RuntimeError로 바꾸고 로그에는 오류 개수만 남겼으므로 기존 화면만으로 원인을 확정할 수 없습니다.

공식 문서에 따르면 ITAD는 요청 한도를 적용하고 제한 시 HTTP 429와 Retry-After를 반환합니다. 실제 한도와 사용량은 ITAD 앱 설정 화면에서 확인합니다. 이번 변경은 요청 간격과 대기를 보완하며, 외부 사이트의 403/5xx, 지역 판매 중단, 응답 형식 오류 등까지 성공으로 표시하지 않습니다.

서버 업데이트 전 기록을 확인하려면 다음을 실행합니다. 환경 파일이나 키 내용은 공유하지 않습니다.

```bash
cd ~/dealnaru-release/dealnaru
sudo docker compose logs --since 12h --tail=120 api
```

업데이트 후 관리자에서 한 번 실행한 뒤 HTTP 상태가 포함된 새 로그를 확인합니다. PARTIAL은 일부 단계가 실패했음을 의미합니다. 스케줄 실행 완료와 별도 대기열의 과거 이력 처리 완료는 서로 다를 수 있습니다.

## 적용

이번 배포용 ZIP의 apply_update.py는 현재 코드와 수정 파일을 비교한 뒤, DB 덤프와 기존 코드, API 로그를 ~/dealnaru-update-backups 아래에 비공개로 보관하고 파일을 교체합니다. .env의 키나 회원/가격 DB를 초기화하지 않습니다. 마지막으로 api/web을 다시 빌드합니다. 서버의 기존 파일이 예상 버전과 다르면 덮어쓰지 않고 중단합니다.

ZIP의 changes 폴더 안에 있는 backend, frontend, compose.yaml, docs를 GitHub 저장소의 같은 위치에도 반영합니다. 그러면 이후 업데이트에서도 이번 수정이 유지됩니다. 배포용 도구와 manifest.json은 운영 설정이나 비밀키를 포함하지 않습니다.

기존 오류의 근본 원인을 확정하려면 보존된 서버 로그 또는 HTTP 상태가 표시된 새 수집 결과를 함께 확인해야 합니다.

참고: https://docs.isthereanydeal.com/ 의 Rate Limiting 절.
